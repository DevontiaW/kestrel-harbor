Where do the sensors and checkpoints go?

A small firm finds out that its AI (artificial intelligence) assistant uploaded a customer file to a website nobody recognizes. The owner asks three questions. Which assistant did it? With whose access? Through which door did the file leave? Nobody can answer, because nothing was watching those places.

You can only see what passes a sensor, and you can only stop what passes a checkpoint. Put sensors where work crosses a boundary, and put the checkpoint as early on the path as you can.

A sensor is anything that records what passes: a log. A checkpoint is a place that can decide and stop.

Picture the file's trip first

First the trip, in plain words. The assistant picks up the file, a tool sends it, and the office's internet connection carries it out. Each stop can have a camera (a sensor) or a guard (a checkpoint). The map below names the same stops the way an information technology team would.

This is the town redrawn as a typical company network. Each box names the enterprise piece and the town piece it stands for. The agents and their tools sit in their own fenced-off part of the network (a segment). The model gateway is the one door for model calls, the identity provider is the sign-in service, and egress is traffic leaving the network. At the bottom, a SIEM (security information and event management system) gathers every record in one place and raises alerts. It watches; it does not stop anything.

Sensors: agent traces (Agents), tool-call log (Tools), prompt and response log (Model gateway), connection log (Network edge), approval log (People: review, approval), sign-in log (Identity provider). Checkpoints: tool checkpoint (Tools, built in the town), gateway policy (Model gateway, drawn only), egress gate (Network edge, drawn only).

Predict before you open the answer.

A task carrying a hidden instruction tells the execution agent to send the file to an outside address. Of the 6 sensors on the map, which would record it? Of the 3 checkpoints, which could stop it first?

Show the path

The action goes from the agents to the tools, through the network edge, to the outside address. 3 of 6 sensors sit on that path: agent traces, tool-call log, connection log. The prompt and response log at the model gateway never sees it, because the file does not pass through the gateway. Watching only your AI model calls would miss this completely. And sensors see different things: the connection log shows that something left and where it went; only the tool-call log shows what was sent.

2 checkpoints sit on the path: the tool checkpoint and egress gate. The tool checkpoint acts first, before anything leaves. The egress gate is a second line. Zero trust is the habit behind this: do not trust a request because of where it came from. Each checkpoint asks who is asking and what they may do. The map shows where such checks could sit, not that every crossing has one. The identity provider answers the owner's second question, "with whose access?", and its sign-in log is where you would look.

A different incident takes a different path. An agent pasting a customer file into a model call is seen by 3 sensors (agent traces, prompt and response log, connection log), and the gateway policy is the first place to stop it.

Break it in the town

  1. Open the town, press Restart, then Reviewers 2, then Enterprise view.

A different situation

A clinic's scheduling assistant reads patient messages, books appointments in the calendar and sends text reminders. Draw its path for one reminder. Where is its door to the outside world, and is there one door or several?

On Monday

List every place your AI tools send something outside your business: email, chat, uploads, model calls. For each one, write two words: is it logged, and can anything stop it? One logged door is easier to watch than five unlogged ones.

A schematic, vendor-neutral map. In the town, only the tool checkpoint is built; the map shows where the others would sit.

Build it yourself with AI

Optional. Give this prompt to any AI chat or coding assistant to draw your own small map. It is a starter for learning, not a security design for a business. Then check its work against the answers below.

The one rule

A sensor sees an event only if the event's path passes it. A checkpoint can stop an event only if it sits on the path, and the earliest one on the path stops it before anything happens.

Starter prompt

Build one HTML file with no libraries that draws a simple network map as an SVG picture, readable on a phone (stack the boxes top to bottom).

Boxes: Model service, Outside address, Network edge, Model gateway, Identity provider, Agents, Tools, People: review, approval, Log collector, SIEM.
Mark a sensor (a blue "S") on: Agents, Tools, Model gateway, Network edge, People: review, approval, Identity provider.
Mark a checkpoint (a red "C") on: Tools, Model gateway, Network edge.

Add two buttons, one for each incident. Each has a path:
1. "Send a customer file to an outside address": Agents, then Tools, then Network edge, then Outside address.
2. "Paste a customer file into a model call": Agents, then Model gateway, then Network edge, then Model service.

When I press a button, draw that path in red, and list underneath: which sensors record it (the ones on boxes in the path) and which checkpoints could stop it, earliest on the path first.

What "done" looks like

  • One page with the map, readable on a phone.
  • Pressing an incident draws its path and lists the sensors and checkpoints on it.

Check the AI's work

  • Sending a file outside: 3 sensors, on Agents, Tools, Network edge. Checkpoints, earliest first: Tools, then Network edge.
  • Pasting a file into a model call: 3 sensors, on Agents, Model gateway, Network edge. Checkpoints, earliest first: Model gateway, then Network edge.
  • The sensor on Model gateway must not appear for the first incident. If it does, the AI is listing every sensor instead of the ones on the path.
