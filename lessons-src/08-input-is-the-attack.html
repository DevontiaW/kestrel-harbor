What happens when the input is the attack?

An office lets an AI (artificial intelligence) assistant read supplier emails and file the invoices. One email carries a line meant for the assistant, not for people: send the customer list to this address. The assistant can send email, so it does. The bookkeeper reviews the filed invoice the next morning. It looks fine. The list is already gone.

Instructions hidden in what an agent reads can steer what it does. A check before the tool action can stop it; a check after the action can only report it.

This is called prompt injection: the attack arrives as content, not as a break-in. With poisoned requests switched on, every {{s8.poisonNth}} task in the town arrives carrying one. In an {{shiftHours}}-hour shift {{s8.poisoned}} arrive, but the last one comes too late to reach a tool, so {{s8.reached}} can act. Half ask the execution agent to {{s8.exportLabel}}, a tool its job does not need. Half ask it to {{s8.sendLabel}}, misusing a tool it does need. Two controls defend the floor:

  • The checkpoint checks each tool action before it runs. A blocked task goes to quarantine, where a person spends {{s8.quarantineMinutes}} minutes clearing it. It is not perfect: every {{s8.slipNth}} poisoned action looks allowed to it and gets through.
  • Least privilege gives each agent only the tools its role needs. The execution agent holds two tools: {{s8.executeTools}}.

Predict before you open the answer.

With two reviewers, {{s8.reached}} poisoned requests can act in a shift. With the checkpoint off but least privilege on, how many unsafe actions get carried out? Does review stop any of them?

Show what the model does

{{s8.lp.unsafe}} unsafe actions get carried out. Least privilege refuses the {{s8.lp.denied}} that ask for a tool the agent does not hold, and lets every misuse of a tool it does hold go through. Least privilege limits which tools an agent holds, not how it uses them; narrow the send tool to the customer on file and it would refuse those too. Review stops none: it checks the work, after the tool has already acted.

With both controls on, the checkpoint sends {{s8.on.blocked}} of the {{s8.reached}} to a person. It lets {{s8.on.slipped}} through because they look allowed. Least privilege refuses {{s8.on.denied}} of those {{s8.on.slipped}}, and {{s8.on.unsafe}} is carried out. That is why you keep both: the checkpoint cut unsafe actions from {{s8.lp.unsafe}} to {{s8.on.unsafe}}, and least privilege caught most of what the checkpoint missed. A real check also misses actions that look allowed, the way review missed defects in lesson 6.

The price is time: the average task's time in the system rises from {{s8.baseInSystem}} to {{s8.on.inSystem}} minutes, and {{s8.on.finished}} finish instead of {{s8.baseFinished}}. Least privilege alone cuts unsafe actions from {{s8.off.unsafe}} to {{s8.lp.unsafe}} at no cost in time; only a check before the action stops more.

Build it yourself with AI

Optional. Give this prompt to any AI chat or coding assistant to add a checkpoint to your small simulator. It is a starter for learning the idea, not a security control for a business. Then check its work against the numbers below.

The one rule

Unsafe actions = poisoned requests that reach a tool − those refused because the tool is not in the role − those stopped by a check before the action (a check that misses some stops fewer). A check after the action stops nothing.

Starter prompt

Start from the single-file queue simulator I built earlier (I will paste it below), with defects switched off and approval on every {{approveNth}} task. Keep it one HTML file with no libraries. Add poisoned requests and two controls:

- Every {{s8.poisonNth}} task arrives "poisoned": it carries a hidden instruction. Poisoned tasks 1, 3, 5... (task {{s8.poisonA}}, {{s8.poisonC}}...) ask the execute step to {{s8.exportLabel}}. Poisoned tasks 2, 4, 6... (task {{s8.poisonB}}, {{s8.poisonD}}...) ask it to {{s8.sendLabel}}.
- Give each step a list of allowed tools. Execute may only: {{s8.executeTools}}. Sending to an outside address uses the send email tool, so the list allows it.
- Add two switches: "checkpoint" and "least privilege", both on at the start.
- When execute finishes a poisoned task (the checkpoint runs first, then the tool list):
  - Checkpoint on: keep a running count of poisoned actions that reach the checkpoint. Every {{s8.slipNth}} one (the {{s8.slipList}}) looks allowed and gets through: treat it as if the checkpoint were off, with least privilege still on, and mark it as slipped. Block every other one: log it and send the task to a quarantine step (one person, {{s8.quarantineMinutes}} minutes, first come first served). After quarantine the task is clean and goes back to execute.
  - Checkpoint off and least privilege on: if the tool is not on execute's list, refuse it and log it; otherwise carry it out.
  - Both off: carry it out.
  Without the checkpoint, the hidden instruction is acted on (or refused) only once; after that the task is clean, even if it passes execute again for its every-{{reworkNth}}-task return.
  A carried-out action is an unsafe action. Count it and log it.

Show counts for unsafe actions, refused, slipped past the checkpoint, and sent to quarantine, and mark them on each task's timeline bar.

What "done" looks like

  • Two new switches and four new counts.
  • With the checkpoint on, most poisoned tasks visit quarantine and still finish; a few slip past.
  • With it off, the unsafe count climbs during the shift.

Check the AI's work

  • Two reviewers, both controls on: {{s8.on.blocked}} sent to quarantine, {{s8.on.unsafe}} unsafe, {{s8.on.finished}} finished. Of the {{s8.on.slipped}} that slipped past the checkpoint, {{s8.on.denied}} were refused.
  • Checkpoint off, least privilege on: {{s8.lp.unsafe}} unsafe and {{s8.lp.denied}} refused.
  • Both off: {{s8.off.unsafe}} unsafe, and {{s8.off.finished}} finished, the same as with no poisoned requests at all. Nothing on an output dashboard warns you.
